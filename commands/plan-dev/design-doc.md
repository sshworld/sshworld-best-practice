# 설계 문서 템플릿 (`~/.claude/design/<repo>/<slug>.md`)

plan 파일은 기계용 물류(Slice File Map, dispatch 인자)가 앞에 오고 작업 후 폐기된다. **설계 문서**는 사람용이고 **작성자 개인 머신에 영속**한다 — 나중에 "이 기능을 왜 이렇게 만들었는지" 되짚기 위한 **개인 작업 기록**이다.

> 기본 경로는 repo 밖(`~/.claude/design/<repo>/`)이다. repo 에 커밋하면 공개 저장소에서는 개인 노트가 그대로 공개되고, 팀 저장소에서는 다른 사람에게 읽기·유지를 강요하게 된다. 팀과 공유할 문서라면 `CBP_DESIGN_DIR` 로 repo 안 경로를 **명시적으로** 지정한다.

---

## (0) 게이트 판정 · 절차 · 한계 (Phase 1-1.5)

**게이트 판정은 파생 규칙이다** — type 별 표를 만들지 않는다:

> 조건부 블록(원인분석 / 구조 델타 / 결정 갈림길 / 기준선) 중 **하나라도 필요하면** Phase 1-1.5 필수 = **2게이트**(설계 승인 → plan 승인). 전부 불필요하면 **fast path**(1게이트, 기존 흐름).
>
> 전부 불필요한 작업 = 원인 자명 + 구조 불변 + 대안 없음 + 잴 것 없음 = rename·문서 이동·설정값·버전 bump.

commit type 으로 가르지 않는 이유: fix 도 도메인 구조를 바꿔 고치면 아키텍처 승인이 최우선이고, type 목록에 `perf` 가 없어 성능 개선이 fix 로 들어온다. 규칙을 2개(게이트 표 + 템플릿 표) 따로 두면 반드시 서로 어긋나므로 하나에서 파생시킨다.

**절차**:
1. `~/.claude/design/<repo>/<slug>.md` 작성 (경로 override: `CBP_DESIGN_DIR`).
2. 사용자에게 제시하고 **AskUserQuestion 으로 승인**. 승인 없이 Phase 1-2 진입 금지.
3. 승인 후 latch — Phase 5 push 게이트가 이 latch 로 실측 write-back 을 판단 강제:
   ```bash
   ${CLAUDE_PLUGIN_ROOT}/scripts/plan-dev-session.sh set-design <설계 문서 절대경로>
   ```

**hotfix 예외**: 착수 전엔 **골격만**(증상 + 가설 + 즉시조치) 승인하고 원인 분석·재발방지는 사후 채운다. 게이트를 없애는 게 아니라 순서를 미루는 것 — 기록 없이 흘려보내지 않는다.

**⚠️ 하네스 한계 자백**: `PostToolUse:ExitPlanMode` 가 이 빌드에서 발화하지 않아 설계 승인 시점을 hook 으로 잡을 수 없다. Phase 1-1.5 는 **콘텐츠 전용 강제**이고, 하네스는 Phase 5 push 게이트가 백스톱이다 — 승인 없이 진행한 세션은 push 단계에서만 걸린다.

**plan 파일과의 역할 분리**: plan 의 독자는 implementor/자식 surface 다 — 물류(Slice File Map·machine-checks·Explored Files)가 거기 남는다. 사람이 판단할 내용(요구·구조·결정·기준선)은 설계 문서에 있고 그쪽이 영속·누적된다. 배경 서술을 plan 에 중복하지 말고 링크만 둔다.

**실측 write-back (Phase 4-0)**: 기준선 형태가 실측 형태를 결정한다 — 수치→재측정값, 재현 절차→절차 실패 확인 + 회귀 테스트명, 관측 증거→증거 소멸 여부. 측정 불가면 `미검증 — 재발 감시 중` 명시. 빈 칸·`TODO`·괄호 자리표시자는 Phase 5 게이트가 차단. **선택 단계(Phase 3.5)에 두지 않는 이유**: reviewer 를 건너뛰는 세션이 필수 동작을 같이 건너뛴다.

## (a) 파일 단위 판정 — 설계 문서 1개 = 기능 1개

slice 는 이 아래의 하위층(구현 편의 분해)이다. 판정 순서:

| 판정 | 규칙 |
|---|---|
| 롤백 단위 | 이 중 하나만 되돌릴 수 있어야 하면 별개 파일. 같이 되돌려야 의미 있으면 한 파일 |
| 수치 공유 | 같은 baseline/목표 표를 쓰면 한 기능. 각자 다른 걸 재면 별개 |
| 한 줄 서술 | 나중에 한 줄로 "무엇을 왜 했는지" 설명할 단위 = 파일 1개 |

한 프롬프트에 기능 3개 넘으면 프롬프트 분해 신호 (200줄 캡이 slice 분해 신호인 것과 같은 꼴).

경로는 `CBP_DESIGN_DIR` env 로 override, 기본 `~/.claude/design/<repo>/`.
**repo 안에 두지 않는 것이 기본**이다 — 개인 기록이므로.

## (b) 템플릿 본문 (그대로 복사)

```markdown
# <기능명>

포함: 원인분석 ✓ / 구조델타 ✓ / 결정갈림길 ✓ / 기준선=관측증거
<!-- 생략한 블록은 ✓ 대신 사유 한 줄. 예: 원인분석 생략(원인 자명) -->

## 1. 요구 또는 증상            [항상]
## 2. 원인 분석                 [조건] 원인이 자명하지 않을 때
## 3. 구조 델타 (지금 → 이후)   [조건] 파일·모듈·데이터 흐름 경계가 바뀔 때
## 4. 결정 갈림길               [조건] 대안이 2개 이상이었을 때
## 5. 착수 전 기준선            [조건] 아래 3형태 중 하나
## 6. 결과                      [항상] 목표 / 실측 — 완료 후 write-back
```

`포함:` 줄은 어느 조건부 블록을 넣었는지 한눈에 보여주는 헤더다. 넣은 블록은 `✓`, 생략한 블록은 **사유 한 줄**을 강제 — 생략 이유를 안 쓰면 "안 썼는지 몰랐는지" 구분이 안 된다.

## (c) 조건부 블록 4개 — commit type 으로 가르지 않는다

**중요**: `feat`/`fix`/`refactor` 로 템플릿을 나누지 않는다. 이유:

- fix 도 도메인 구조를 바꿔 고치면 구조 델타가 필수
- type 목록에 `perf` 가 없어 성능 개선이 fix/refactor 로 들어온다
- feat 도 기존 동작 규명이 선행되면 원인 분석이 필요

즉 조건은 **commit type 이 아니라 이번 변경의 실제 내용**이다.

| 블록 | 조건 | 생략 시 표기 |
|---|---|---|
| 원인 분석 | 원인이 자명하지 않을 때 | `원인분석 생략(원인 자명)` |
| 구조 델타 | 파일·모듈·데이터 흐름 경계가 바뀔 때 | `구조델타 생략(경계 불변)` |
| 결정 갈림길 | 대안이 2개 이상이었을 때 | `결정갈림길 생략(대안 없음)` |
| 기준선 | 항상 3형태 중 하나 선택 (완전 생략 불가) | — |

---

## (d) 기준선 3형태

기준선의 목적은 **재현이 아니라 완료를 판정할 고정점**이다. 재현이 안 되거나 불필요해도 기준선은 항상 있어야 한다.

| 형태 | 조건 | 예 | 완료 판정 |
|---|---|---|---|
| 수치 | 정량 목표 | p95 820ms | 재측정해서 델타 |
| 재현 절차 | 재현 가능한 결함 | 스텝 3개 → 표 오버플로 | 절차가 이제 실패 |
| 관측 증거 | 재현 불가·불필요 | 프로덕션 로그 1건, `foo.css:12 min-width:auto`, 정적분석 출력 | 증거가 사라짐 / 재발 감시 |

증명 불가한 완료(수치도 재현도 안 되는 경우)는 감추지 말고 6번 결과에 **`미검증 — 재발 감시 중`** 을 그대로 쓴다.

---

## (e) 결정 갈림길 — 4칸

`선택 / 버린 대안 / 이유 / 뒤집는 비용`

`뒤집는 비용` 칸이 없으면 모든 결정이 같은 무게로 보여 사용자가 전부 읽거나 아무것도 안 읽게 된다 — 되돌리기 비싼 결정만 먼저 읽도록 신호를 줘야 한다.

| 선택 | 버린 대안 | 이유 | 뒤집는 비용 |
|---|---|---|---|
| (예시) A | B | ... | 낮음/중간/높음 + 한 줄 근거 |

## (f) 결과 — 목표 / 실측 write-back

```markdown
| | 목표 | 실측 |
|---|---|---|
| ... | ... | (S4 에서 채움) |
```

실측은 Phase 3.5~4 에서 채운다. 실측 형태는 기준선 형태가 결정한다 — 수치 기준선 → 재측정 수치, 재현 절차 기준선 → 통과한 회귀 테스트명, 관측 증거 기준선 → 감시 결과(또는 `미검증 — 재발 감시 중`).

## (g) mermaid 규약

- **노드 개수를 제한하는 규칙은 두지 않는다.** 한 기능이 여러 노드를 건드리면 그게 사실이고, 모아 봐야 구조가 보인다. 노드를 줄이라고 강제하면 구조를 숨기는 결과만 된다.
- 가독성 축은 **엣지 교차**다. 엣지가 subgraph 경계를 3회 넘게 역방향으로 넘으면 그룹 재분류 신호(노드를 줄이라는 게 아니라 다시 묶으라는 신호).
- 노드 라벨은 번호 앵커(`①`)로 짧게, 설명은 그림 밖 표로 뺀다.
- 기본 config 블록 (그대로 복사):

```
---
config:
  layout: elk          # 렌더러가 elk 를 등록했을 때만 적용. 아니면 조용히 dagre 로 폴백 — 아래 실측 참조
  flowchart:
    nodeSpacing: 60
    rankSpacing: 90    # 여백 체감 대부분이 여기서 나온다 (기본 50)
    curve: stepBefore
---
```

**렌더러별 실측 (2026-08-14, 같은 그래프 A/B)**

| 렌더러 | elk 등록 | 결과 |
|---|---|---|
| Obsidian (`mermaid@11.4.1` + `registerLayoutLoaders`) | O | `flowchart LR` 이 지켜져 **가로 814×376 (비 2.16)** — subgraph 두 개가 나란히 |
| GitHub | **X** | 조용히 dagre 폴백 → **세로 426×1395 (비 0.31)** — LR 무시, 길게 늘어짐 |

**에러로 뜨지 않는다 — 조용히 나빠진다.** 그래서 "깨지면 지워라" 로는 못 잡는다. GitHub 에서 읽힐 문서라면 subgraph 두 개를 나란히 놓는 구성 자체를 피하고, 다이어그램을 둘로 쪼개는 편이 안전하다.

**라벨에 `<` `>` 금지** — mermaid 가 HTML 태그로 먹어 통째로 사라진다. 실측: `docs/design/&lt;slug&gt;.md` → `docs/design/.md` 로 렌더됨. **`docs/design/[slug].md` 처럼 대괄호를 쓴다.**

- 원본/렌더 분리: mermaid 가 in-repo **원본(진실)**. SVG/FigJam 렌더는 마일스톤 opt-in. **둘이 어긋나면 텍스트가 진실.**

### 흐름이 주제일 때 — `architecture-trace` (opt-in, 별개 산출물)

mermaid 는 **구조**를 그린다. 요청이 어느 경로를 타는지, 어디서 실패하는지, 지연이 어디서 쌓이는지 — **행위**는 표현 수단이 아예 없다. 이건 mermaid 숙련도 문제가 아니라 표기법에 없는 정보다.

그런 작업이면 `architecture-trace` 스킬로 애니메이션 트레이스를 **추가로** 만든다. 규칙:

- **3번 구조 델타를 대체하지 않는다.** 노드 몇 개짜리 `지금 → 이후` 그림에 애니메이션을 얹으면 정보량만 늘고 더 안 읽힌다. 흐름·분기·실패 경로가 있을 때만.
- **생성물이다 — 동기화 의무 없음.** 엣지 좌표 산술이라 노드 하나만 옮겨도 깨진다. 원본은 여기 mermaid 고, 트레이스는 발표·온보딩·RFC 처럼 볼 사람이 정해진 순간에 재생성한다.
- 값의 핵심은 시각효과가 아니라 **실패 시나리오를 강제로 열거하게 만드는 것** — 위 기준선 3형태·`미검증` 자백과 같은 뿌리다.
